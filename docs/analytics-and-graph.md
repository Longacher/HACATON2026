# Графовые БД для связей между тикетами

## Задача
Соотношения между обращениями: «этот тикет — вероятный дубль того», «податель
пишет о продолжении той же травли», «связанные инциденты», «цепочка передач
между специалистами».

## Сравнение

| БД | Сильные стороны | Слабые | Когда брать |
|---|---|---|---|
| **Neo4j** | стандарт де-факто, Cypher, зрелость, индексы, плагины, драйвер `neo4j` | отдельный сервис, память | основной выбор для MVP хакатона |
| **Memgraph** | Cypher-совместим, быстрый, лёгкий | моложе, меньше сообщество | стриминг/real-time |
| **ArangoDB** | граф + документы + поиск в одном | AQL вместо Cypher | мультимодель |
| **FalkorDB** | in-memory на Redis-модели, предельно лёгкий | объём ограничен памятью | совсем лёгкий MVP |
| **Amazon Neptune** | managed | lock-in в AWS | не для локального хакатона |
| **TigerGraph/JanusGraph** | мощные, распределённые | сложная настройка | избыточно |

**Рекомендация для проекта: Neo4j** (реализовано в `app/services/graph.py`).

## Модель данных

```
(:Appeal {id, textPreview})
  -[:DUPLICATE_OF]-> (:Appeal)     # вероятный дубль (по эмбеддингам Milvus)
  -[:RELATED_TO]->   (:Appeal)     # связанный инцидент / цепочка
(:Specialist {id}) -[:WORKS_ON]-> (:Appeal)   # нагрузка, передачки, история

# Анонимность: персон в графе нет. Псевдоним/дубли связываются через хеш-сигнатуру
# содержания, без IP/имён/контактов.
```

## Как решает задачи ТЗ

- **«Потенциал»**: связность обращений показывает «мульти-инцидентность» —
  один и тот же контекст переходит между разными заявителями.
- **Дубли** (оператор отсеивает): поиск похожих по эмбеддингу → `DUPLICATE_OF`.
- **Цепочки**: `RELATED_TO` позволяет эксперту видеть похожие случаи и рекомендовать
  соисполнителя.

# Аналитика и способы вывода

## Пайплайн сбора

```
События (appeal.created, status_changed, return, crisis, transfer)
   │
   ▼ RabbitMQ (topic: otklik.events)
   │
   ├── analytics_queue ───► Redis-агрегаты (все счётчики дашборда)
   │                          (hincrby: total, by_category, by_status, by_type,
   │                           urgent, crisis, returns; today по дням)
   │
   └── index_queue ──────► Milvus (эмбеддинг текста → поиск похожих)
                          └──► Neo4j (узел Appeal + RELATED_TO к похожим)
```

Исторические метрики (средние времена отклика/закрытия) считаются по PostgreSQL
в `AnalyticsService` (сервис `analytics.py`).

## Метрики дашборда (ТЗ 4.6)

- количество обращений за период (и по дням — Redis `today`);
- распределение по категориям, типам заявителей, статусам;
- среднее время до принятия оператором / до первого ответа / до закрытия;
- нагрузка по операторам и экспертам;
- доля срочных, доля кризисных, доля возвратов.

## Способы вывода

| Канал | Как | Назначение |
|---|---|---|
| REST JSON | `/admin/analytics?period_days=` | дашборд в веб-интерфейсе |
| CSV/XLSX | `/admin/report.csv` | обезличенная выгрузка (без текстов/контактов) |
| WebSocket live | ключ `/ws/analytics` | живое обновление счётчиков |
| Prometheus | экспортер поверх Redis-агрегатов | мониторинг (опционально) |
| Grafana | источник: PostgreSQL (история) + Redis (live) | BI-дашборды |
| Уведомления | RabbitMQ → push | алерты: зависшие, кризисные без реакции |

## Рекомендации по выводу для жюри

1. **Живые числа** — WebSocket-лента поверх Redis (видно, как приходит новое).
2. **Гистограммы по дням** — из Redis `today` (HINCRBY по дате).
3. **Тайминги** — средние времена из PostgreSQL (признак «мы считаем SLA»).
4. **Доступ**: аналитику видит только админ (ТЗ).
